## 怎么跑（e16）

都在 Colab A100（40GB 即可）上，按这个顺序：

1. `Qwen38_pi_ContrastPairs.ipynb`，第 1 节 `STAGE = "pairs"`，从头运行。pi 开思考解 570 道难题（440 道各 4 次、130 道留出题各 2 次；题源见下面“题目为什么换成难题”），写出对比对，最后打印 `CONTRAST_PAIRS_FILE = "…"`。
2. 融合 notebook：把那一行填进第 1 节（`TRACE_LORA_DIR` 和 `tm_extra2["code_sha256"]` 已按 e15 里填的预填，核对一下是否一字不差），从头运行。全局搜索、ν、ν₂、分量筛选都按对比目标做；最后把选中的候选（分量筛选改了 F 时再加上 F）存到 `DRIVE_DIR/veto/`，返回 `waiting_for_veto`。
3. 对比对 notebook，`STAGE = "veto"`，从头运行：候选在 130 道留出题上开思考生成，写出 `DRIVE_DIR/veto/result.json`。
4. 融合 notebook 再从头运行：通过的候选从 Drive 上的副本上传（搜索和分量筛选不会重做），然后照常做 FP8。

## 这次（e16）改了什么

**为什么**：e15 的目标是“不开思考时，数据集参考答案的 NLL”。在 Colab 上评完前几个候选后逐类、逐题看：六类题的 NLL 都随融合强度单调下降（例如逻辑类 2.98 → 0.75、代码类 1.44 → 0.31），48 题全部同向，最优点落在网格边缘。它量的主要是“像不像参考答案的格式”，不是推理。

**新目标**：S（pi）自己开思考解题，每题取一条做对、一条做错的推理（长度相差不超过 2 倍，被截断或答案读不出的不用）。候选在这些推理上算 **NLL(对的) − NLL(错的)** 的平均，越低越好：两条都出自 S，格式和文风抵消，剩下的是推理对不对。护栏：对的推理本身的平均 NLL 不能比 S 高 5% 以上（`tau`）；任何一类比 S 差超过 0.01 的候选不算数。这是 teacher forcing（在 S 的推理上打分，不是候选自己生成），候选离 S 越远越不准，所以上传前再用生成把关：200 道留出题、开思考，正确率比 pi 低 5 个百分点以上的不上传。

**改了哪些模块**（评分和选型的四个；`qmerge_tm` / `qmerge_tm2` 只加了复用缓存前的核对，见下面“外部检查报告”；其余 5 个与 e15 逐字节相同，测试里核对指纹）：
- `qmerge_core`：对比对文件的格式检查；对比对直接用存下的 token id 打分，不重新切词。不改 `VERSION`。
- `qmerge_runtime`：最后的 logits 每次只算 2048 个位置（长推理不会一次占用“长度 × 24 万词表”的显存）；隐状态放不下显存时放 CPU 内存、轮到时再搬上去；上一个候选最后一层的隐状态留在内存里（`RamLayerMemo`），只换输出头的补评不再跑一遍主干（本地盘被 S、D、C、B 占满，原来写盘的缓存在这里写不进去，12 次补评会各多一次完整前向，约 3–4 小时）。
- `qmerge_components`：损失对最后隐状态的梯度也分段算；梯度这一步的隐状态可以放在另一个目录（本地盘），换了会话、隐状态不在了就从前向重来；GPU 上一段的输入放 CPU 内存；不再需要的隐状态文件提前删掉。
- `qmerge_pipeline`：问题的单位是“一对推理”（目标、类别均值、bootstrap、两折交叉拟合、变体评分都按对算）；护栏进入搜索、ν / ν₂ 线搜索、分量筛选所有的可行性判断；搜索用的对超过 90 万 token 时、分量筛选用的对超过 20 万 token 时，按类轮流整对选一部分；分量筛选的方案改为宽松、步长 0.5、步长 1；GPU 上用 float32 + TF32、SDPA 注意力；生成把关的交接（`veto/request.json`、`veto/result.json`）。`objective = "contrast"` 时没有对比对就停下，不会退回旧目标；`objective = "reference_nll"` 时不理会还填着的对比对路径；在 CPU 运行时上不开始（返回 `needs_gpu_runtime`，否则每个候选要在 CPU 上算几十个小时）。

**对比对 notebook 的生成把关**：按偏好顺序评，第一个通过就停；vLLM 在同一个进程里先后加载两个 27B 模型时显存不一定能释放干净，所以一次运行只加载一个候选，第一个没通过时提示“重启会话”后再运行一次；生成的批次存在 Drive（`veto/samples/`），断开后接着做。

**缓存**：D、C、N、N₂ 的缓存身份不含这些模块的代码哈希（由 `AUX_DELTA_VERSION`、各自的版本和输入决定），继续有效；`inputs.json` 的输入绑定也不变。S 的基线、反向自检、搜索候选、分量筛选的缓存身份含 `qmerge_core` / `qmerge_runtime` 的代码哈希和评分选项，会在 A100 上按新目标重新算。

### 题目为什么换成难题（2026-11-05）

第一次采样用的是 MATH 3–5 级（数论、代数）、BBH、CRUXEval、C-Eval 理科和 MMLU-Pro。pi 的正确率是 95%：600 道题里 572 道 4 次全对，只凑出 19 对，其中逻辑类只有 2 对，不够融合 notebook 用（至少 40 对、每类至少 3 对）。

现在换成 pi 大约能做对一半到八成、考推理而不是考记忆的题。研究生水平的知识题不用：27B 做错多半是因为不知道某个事实，做对也可能是蒙的，这样的“对 / 错”对比不出推理。

|---|---|---|
| 数学 | Omni-MATH 里的数论题，难度 ≥ 4，答案是整数，去掉问两个量却只给一个答案的题（可用约 340 道） | 130 / 40 |

题目在本地用真实数据跑过一遍选题：每类合格题都够，题目里的选项、答案格式都对。新题对应新的运行目录，第一次那 19 对和它的采样仍在 Drive 上，但不混进来。vLLM 的设置也调了：每批 128 道题（每批要等最长的那条写完，批大了空转少），显存比例 0.93，纯文本模式；引擎启动失败时先用同样的设置再试一次（冷启动常常第一次失败），只有参数不被接受时才换设置。

### SenseNova 部分的设计取舍

- **供体前向**：用作者的远程代码跑完整前向，在每个 `nn.Linear` 投影上挂 hook 取实际的输入和输出（按篇取均值），不手写线性注意力和 mHC。运行前：固定 commit；审读代码，并把代码摘要写进设置；独立子进程；transformers 5.18 单独装在本地临时目录，本内核的版本不变。权重按检查点精度放在内存里（约 18GB），每个解码层只在运行时临时转成 float32，计算精度与 Nanbeige 相同，内存约 26GB。
- **前向闸门**：Nanbeige 的 4 条短提示，加上原生精度前向与 float32 前向的 logits 对照（余弦 ≥ 0.98、top-1 相同），再加上按模型卡核对实际观察到的执行顺序（56 次）、层数、宽度、头数、词表和 3:1 混合注意力。任何一项不符都停下，不凭猜测硬编码。
- **共享权重的层**：56 次执行各算一个候选供体层（深度按执行位置），参加 CKA 预筛和 OT。注意力在每次全注意力执行都记录（14 次），MLP 每隔一次执行记录（28 次）。一份物理层的权重可以搬到多个目标层。
- **模块**：v/o/gate/up/down 与 N 相同；k_proj 在头维、旋转维和 M-RoPE 布局都与 B 相同，且激活仓里有 B 的 k_proj target 激活时才搬（`auto`），否则写明原因后不搬；线性注意力的投影不搬，因为共用的激活仓里没有 B 线性注意力层的 target 激活。
- **ν₁、ν₂ 怎么评**：依次线搜索：先在获胜配方上评 ν（3 次），再在“获胜配方 + 选中的 ν·N”上评 ν₂（3 次），共 6 次。3×3 联合网格要 9 次；每次评分约 1–2 小时，依次评少 3–6 小时（约 0.5–0.9 单元）。N 和 N₂ 都只改每张矩阵的 128 行、幅度很小，而且多半是不同的行，二者的相互作用是二阶的。ν₂ 必须 > 0（取 NLL 最低的可行值）。
- **耗时**：N₂ 约 10–21 小时（激活 6–13 小时，OT 与融合 4–8 小时），约 1.5–3.2 单元；ν₂ 线搜索另加 3–6 小时。合计由 9–19 单元变为约 11–23 单元。

跑过之后请看 `DRIVE_DIR/aux_delta/<指纹>/aux_delta_report.json` 里 DELLA 组各成员的增量范数：DarwinRSI 的（对 Qwen3.5-27B 取）如果比其他成员大好几倍，说明它的训练底座可能不是 Qwen3.5-27B，告诉我。

**转换**（`convert_mcp_universe.py`，只用标准库）：每次运行重建一段标准多轮对话。每一步的思考、正文、工具调用取自那次调用的 API 响应；工具返回取自下一次调用的请求历史，即模型实际看到的文字（网页搜索和浏览器自动化里，框架先让模型改写原始返回再放进上下文，用的是改写后的版本）；框架每步插入的“还剩 N 步”提示默认去掉，这样每一步的思考都按 Qwen 的格式保留。工具定义没有记在日志里，按领域汇总实际出现过的调用补出最简定义。748 次里转换成功 746 次（跳过的 2 次都是失败运行，某一步的工具调用在下一次请求里没有返回），通过的 289 次全在。按 32k 上限约保留 241 次（4-bit 底座），按 16k 约 161 次。

**两个 notebook 的分工**

| notebook | 运行时 | 做什么 |
|---|---|---|
| `StartLux_trace_LoRA.ipynb`（新） | 一张 80GB 显卡（H100、A100/A800 80GB、H800）或 H200。RunPod、Vast.ai、AutoDL 或 Colab 都可以：不在 Colab 上时文件放在 `WORK_DIR`，可填 `EXPORT_REPO` 把 adapter 传到私有仓库再放进 Drive；国内平台可设 `HF_ENDPOINT` 镜像。`PRECISION = "auto"`：显存 ≥ 120 GiB（H200、B200）用 BF16 底座，80–96GB 卡用 4-bit 底座，都训到每条 32k token；开训前先拿最长的一条试一次前向 + 反向，放不下马上报错 | 锁定底座 commit；按评分筛选轨迹（默认只用严格通过的）；用底座的 chat template 渲染完整对话，只在助手回合（思考、工具调用、回答，以及每个回合的结束标记）上算损失；LoRA 加在解码层的注意力、线性注意力、MLP 上；分块算损失（不展开 24 万词表的完整 logits）；断点存 Drive、可续跑；训练前后各算一次留出集损失；导出 adapter + `trace_lora_manifest.json`，最后打印 `TRACE_LORA_DIR = "…"` |
| `Qwen38_pi_AuxMix_e15_FP8.ipynb`（补丁） | CPU 高 RAM | 新的辅料格式 `lora`：读 adapter，每个被改的矩阵按 float32 算 scale·(B @ A)，乘 0.4 加进 D。不先合并成 BF16 模型：小增量会被舍入成噪声，也省得上传 55GB |

**顺序**

1. 现在这一轮等待阶段照常跑（D → C → S 的基线 → N → N₂）。新 notebook 里 `STARTLUX_REQUIRED` 默认 `False`、`StartLuxLoRA` 在等 `TRACE_LORA_DIR`，已经算好的 D 照常沿用。
2. 把轨迹传到 Drive，在训练 notebook 第 1 节改 `DATA_FILES`；先设 `SMOKE_TEST = True` 跑 2 步确认能通，再改回 `False` 正式训练。
3. 训练 notebook 打印的 `TRACE_LORA_DIR = "…"` 填进融合 notebook 第 1 节，在 CPU 高 RAM 运行时上从头运行：DavidAU 和 StartLuxLoRA 一起补加到已有的 D 上，然后搜索、分量筛选、上传。

**它在成品里的分量**：系数 0.4 之外还要乘整个 D 的 λ（0.025–0.2），最终只有训出增量的约 1%–8% 进入成品，与原计划的 StartLux 相同。

**局限**：学到的是这个检查点在这些任务上的行为，不是它的完整后训练；跨一代（3.6 → 3.8）移植会损失一部分效果；只用通过的轨迹时样本少。真实 27B、Qwen3.6 的线性注意力层和 GPU 训练都没有在这里运行过：整条流程（筛选、渲染、只训助手回合、分块损失、训练、续跑、导出、被融合 notebook 读回并与 PEFT 的合并结果逐元素一致）只在 CPU 上用极小的 Llama 测过。
