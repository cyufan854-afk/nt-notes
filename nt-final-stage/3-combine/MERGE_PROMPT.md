# 给合并模型的操作说明（第 3 步：branch1 + branch2 → final.tex）

把本文件整份交给负责合并的前沿模型（Claude / GPT 的 agent 模式，能读写本地文件、能运行命令）。合并由你在文件上逐个单元完成：**不要写自动合并脚本，不要用 `git merge-file` 之类的工具直接产出结果**。下面提到的 `merge_check.py` 只列信息和做检查，不改任何文件。

## 你手上的文件

都在主文件夹 `nt-final-stage/`：

| 文件 | 是什么 | 你能不能改 |
|---|---|---|
| `baseline.tex` | 共同祖先。branch1 和 branch2 都从它分出来 | 不能改 |
| `branch1.tex` | 作者自己这一侧的最新版：多轮前沿模型数学审查、Muse Wonder 一轮、作者的手工修改 | 不能改 |
| `branch2.tex` | 27B 模型那一侧：全文英文润色、DeepSeek 审计表 LOW 条目的初筛修补、引用核查修补 | 不能改 |
| `final.tex` | 你的产物（还不存在，由你创建） | 只写这一份 |
| `3-combine/merge-log.md` | 你的合并记录（由你创建） | 只写这一份 |

这是一份英文 LaTeX 初等数论讲义（约 13,500 行、约 200 页、三百多个定理、一百多个定义）。**三份一起看**：判断一处改动属于哪一边、要不要保留，永远以 baseline 为参照，不要只比较 branch1 和 branch2。

## 先做两件事

1. 在 `3-combine/` 里运行 `python3 merge_check.py plan`，读生成的 `merge-plan.md`：
   - **单元一览**：每个单元（一个定理或定义连同其后的证明，或标题下的一段说明文字）分别被哪一边改过。只有一边改过的单元占绝大多数；两边都改过的单元是你要花时间的地方。
   - **label 对照**：branch1 可能新增了带编号的环境（例如在一个小节里插入了一条新定义），之后的 label 按编号顺延；branch2 保持 baseline 的 label。工具按标题和正文自动配对，**请逐条核对**（自动配对只是建议）。
2. 以 `branch1.tex` 为底稿复制出 `final.tex`，然后逐个单元把 branch2 的改动搬进来。这样 branch1 新增的环境、改过的 label 和导言区天然就对了。

## 逐单元的规则

对每个单元，比较 baseline、branch1、branch2 三份的这一段：

1. **只有一边改了**（另一边与 baseline 相同）：用改了的那一边。不评价改得好不好，也不顺手润色；数学审查是第 4 步的事。
2. **两边都没改**：保持原样。
3. **两边都改了**：按改动块分别处理。
   - 两边改的是不同位置：两处都保留。
   - 改的是同一句话：先弄清每一边想做什么（修数学、补条件、改引用、只是润色）。branch1 的数学修改经过多轮审查，优先保留；branch2 的润色只有在不改变 branch1 那一版的数学含义、能干净地加在 branch1 的文字上时才保留。两边都在修同一个数学问题时，选更正确、更完整的一版，必要时把两边的要点合在一起写成一版（只用两边已有的内容，不引入新的数学）。拿不准就保留 branch1 的版本，把 branch2 的版本原样记进 `merge-log.md` 交给第 4 步。
4. **引用要按 label 对照改写**：从 branch2 搬过来的文字里，凡是 `\ref{…}`、`\eqref{…}` 指向在 branch1 里改了名的 label，都要改成 branch1 的新名字。例如截至写这份说明时，baseline 的 `def:5.7.1`（average order）在 branch1 里是 `def:5.7.2`，branch1 的 `def:5.7.1` 是新增的 asymptotic notation。以你运行 `plan` 时看到的对照为准，branch1 在合并之前可能还会变。
5. **不动 label 和带编号的环境**：label 按编号命名，且与实际编号一致，所以 `final.tex` 里的 theorem / definition 环境及其 `\label` 必须与 `branch1.tex` 完全相同（同样的个数、顺序、名字）。不能新增、删除、拆分、合并或调换带编号的环境，不能改 `\label{…}`。branch2 若在这方面有改动（它本不应该有），不采用，记进日志。
6. **不改数学内容**：合并只决定“用哪一边的文字”，不做新的数学修改。你发现的疑点写进日志，不要动手修。
7. **导言区、宏定义**：以 branch1 为准。branch2 若改了导言区，逐条判断是否必要并记录。

不要为了让任何一方的“保留率”更高或更低而做决定：合并之后会用 `run_retention.py` 统计 27B 和 Muse Wonder 两组改动在最终稿里的保留、撤回和改写比例，这个统计只有在你按内容决定时才有意义。

## 工作方式

- **不要在聊天里输出整份文件**，也不要输出大段的单元全文。直接在文件上编辑（每次只改一个单元的范围），聊天里只报告进度，例如“第 4 章完成，两边都改过的 12 个单元已处理，3 处记入日志”。
- 按单元顺序推进；每完成一章，运行一次 `python3 merge_check.py verify`。
- `merge-log.md` 只记需要人看的事，每条写清单元 id、两边各自的改动、你的选择和理由：
  - 两边都改过同一处、你做了取舍的地方；
  - 你保留了 branch1、放弃了 branch2 某处修补的地方（尤其是 branch2 的 LOW 初筛和引用核查修补，第 4 步要复查）；
  - branch2 改动了 label、编号环境或导言区的地方；
  - 你注意到、但按规则没有动手的数学疑点。

## 完成标准

1. `python3 merge_check.py verify --compile` 全部通过：
   - 没有冲突标记；
   - label 和带编号的环境与 branch1 完全相同；
   - `\begin` / `\end` 配对；
   - 所有引用都能解析；
   - `latexmk -pdf` 编译成功，没有未定义引用和重复 label，label 名与实际编号一致。
2. 只有 branch2 改过的单元，最终稿里是 branch2 的文字（引用已按对照改名）；只有 branch1 改过的单元，是 branch1 的文字。可以抽查 `merge-plan.md` 里的若干行核对。
3. `merge-log.md` 写好。
4. 在聊天里给出一段简短总结：处理了多少个单元，两边都改过的有多少，记入日志多少条，`verify` 的结果。

之后由作者运行 `python3 run_retention.py` 统计留存率，再进入第 4 步的统一审查。
