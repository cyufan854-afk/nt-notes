# 给合并模型的操作说明（第 3 步：branch1 + branch2 → final.tex）

把本文件整份交给负责合并的前沿模型（Claude / GPT 的 agent 模式，能读写本地文件、能运行命令）。你的目标是做出**最好的最终稿**：取舍、融合、回滚、在冲突处重写，以及小幅的数学修正和自行优化，都由你按内容判断。只有下面几条硬约束不能违反，你做的每个实质决定都要说明。

不要写自动合并脚本，也不要用 `git merge-file` 之类的工具直接产出结果。你要逐个单元看过、在文件上动手。`merge_check.py` 是给你的辅助工具，只列信息、做检查，不改文件。

## 文件

都在主文件夹 `nt-final-stage/`：

| 文件 | 是什么 |
|---|---|
| `baseline.tex` | 共同祖先。branch1 和 branch2 都从它分出来（不要改） |
| `branch1.tex` | 作者一侧的最新版：多轮前沿模型数学审查、Muse Wonder 一轮、作者的手工修改（不要改） |
| `branch2.tex` | 27B 模型一侧：全文英文润色，以及经复核后采用的 DeepSeek 审计表 LOW 条目修补和引用核查修补（不要改） |
| `2-branch2/stages/` | （有的话）branch2 的阶段稿：`1-polish.tex` → `2-triage.tex` → `3-refs.tex`，可以看出 branch2 的每处修改出自哪一步 |
| `final.tex` | 你的产物（由你创建） |
| `3-combine/merge-log.md` | 你的说明（由你创建） |

这是一份英文 LaTeX 初等数论讲义（约 13,500 行、约 200 页、三百多个定理、一百多个定义）。判断一处改动是谁做的、改了什么，永远以 baseline 为参照，三份一起看。

## 开始之前

1. 在 `3-combine/` 里运行 `python3 merge_check.py plan`，读 `merge-plan.md`：
   - 每个单元（一个定理或定义连同其后的证明，或标题下的一段说明文字）被哪一边改过；
   - baseline → branch1 的 label 对照。branch1 新增过带编号的环境，后面的 label 顺延；对照是按标题和正文自动配对的，请逐条核对。
2. 以 `branch1.tex` 为底稿复制出 `final.tex`，然后逐个单元处理。

## 硬约束（不能违反）

1. **label 与带编号的环境**：`final.tex` 里的 theorem / definition 环境及其 `\label` 必须与 `branch1.tex` 完全相同，个数、顺序、名字都一样。label 按编号命名，与实际编号一致；不能新增、删除、拆分、合并或调换带编号的环境，也不能改 `\label{…}`。若你认为某处确实需要增删环境，写进日志留给作者。
2. **引用按对照改写**：从 branch2（或 baseline）搬来的文字里，凡是 `\ref{…}`、`\eqref{…}` 指向在 branch1 里改了名的 label，都改成 branch1 的名字。例如截至写这份说明时，baseline 的 `def:5.7.1`（average order）在 branch1 里是 `def:5.7.2`；以你运行 `plan` 时看到的对照为准。
3. **能编译、引用都能解析**：`python3 merge_check.py verify --compile` 全部通过。
4. **不在聊天里输出整份文件**，也不贴大段单元全文；直接在文件上改，聊天里只报进度。

## 你可以自己决定的

- **只有一边改过的单元**：通常采用改过的那一边。但如果你判断那处改动是错的、改坏了、或不如原文，可以回滚，也可以在它的基础上再改。
- **两边都改过的单元**：选一边、把两边融合，或者重写，按你认为最好的来。branch1 的数学修改经过多轮审查，分量较重；branch2 的润色和修补也可能修到了 branch1 没注意的地方。不必默认偏向任何一边。
- **小幅的数学修正**：发现错误、遗漏的条件或步骤、公式笔误时，可以直接改。“小幅”指局部的修正，不改变定理的含义和证明的整体结构。更大的问题写进日志，交给第 4 步。
- **自行优化**：表述、衔接、前后一致性（记号、术语、写法）上的改进可以做，但不要为改而改。

不要为了让任何一方的“保留率”更高或更低而做决定：合并之后会统计 27B 和 Muse Wonder 两组改动在最终稿里保留、撤回、改写的比例，这个统计只有在你按内容决定时才有意义。

## 必须说明的（输出时要说明）

下面这些情形，每一处都在 `3-combine/merge-log.md` 里写一条。格式固定，便于作者和工具核对：

```
- 单元 thm:4.3.1 · 类型：回滚 / 冲突处理 / 新的数学修改 / 自行优化 · 改了什么：（一两句，必要时附改前改后的关键片段）· 理由：（一两句）
```

- **回滚**：只有一边改过、你没有采用（或部分没有采用）那一边的修改。
- **冲突处理**：两边都改过，你选了一边、融合，或者重写。
- **新的数学修改**：两边都没有、由你新做的数学修正（条件、步骤、公式、结论），无论多小。
- **自行优化**：两边都没有、由你新做的非数学修改。
- 另外列出：你注意到、但按“小幅”的界限没有动手的数学疑点；branch2 若改动了 label、编号环境或导言区，你怎么处理的。

单元 id 写最终稿里的 label（说明文字单元用 `merge-plan.md` 里的 id）。`merge_check.py audit` 会逐单元判断最终稿取自 branch1、branch2、baseline，还是新写的文字；凡是“新写”或“回滚了只有一边做过的修改”的单元，日志里都必须提到它的 id，否则 audit 不通过。

## 工作方式

- 按单元顺序推进；每完成一章，运行一次 `python3 merge_check.py verify`。
- 聊天里只报进度，例如“第 4 章完成：两边都改过的 12 个单元已处理，新的数学修改 2 处，记入日志”。

## 完成标准

1. `python3 merge_check.py verify --compile` 全部通过。
2. `python3 merge_check.py audit` 通过：每个需要说明的单元都在 `merge-log.md` 里。`merge-audit.md` 留着给作者看。
3. 在聊天里给一段总结：
   - 处理了多少单元，两边都改过的有多少；
   - 回滚、冲突处理、新的数学修改、自行优化各多少处；
   - **逐条列出所有“新的数学修改”**（单元 id 和一句话）；
   - `verify` 与 `audit` 的结果。

之后由作者运行 `python3 run_retention.py` 统计留存率，再进入第 4 步的统一审查。第 4 步会对每个单元再做一次多模型数学审查。
