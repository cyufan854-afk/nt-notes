# 处理交叉审查的意见（第 4 步的后半）

把本文件交给 agent 模式的前沿模型。最好就是第 3 步做合并的那个，它熟悉自己的决定；它能读写本地文件、能运行命令。

## 材料

- `final.tex`（主文件夹）：第 3 步的合并结果，就在它上面改。
- `baseline.tex`、`branch1.tex`、`branch2.tex`（主文件夹）：只读，用来核对。
- `3-combine/merge-log.md`：第 3 步的合并说明。
- `4-cross-review/reviews/` 里的审查意见：每个审查模型一个文件，文件名就是审查者。每个问题是一个 `<<<FINDING Fn>>> … <<<END Fn>>>` 块，含单元、类别、严重度、final 原文、问题、依据、建议。

## 做法

1. 逐条处理每个审查者的每个问题。不同审查者指出同一处时，合并成一条处理。
2. 审查者也可能出错。先回到 baseline、branch1、branch2 核对事实，再决定：
   - **采纳**：修改 `final.tex`。建议的改法不一定最好，你可以按自己的判断改。
   - **部分采纳**：只改其中成立的部分。
   - **不采纳**：写明理由（例如审查者看错了版本、问题在 branch1 里本来就如此且是对的）。
3. 硬约束与第 3 步相同：
   - `final.tex` 的 label 和 theorem / definition 环境与 branch1 完全相同；
   - 引用按 label 对照改名；
   - 能编译；
   - 不在聊天里输出整份文件。
4. 在 `3-combine/merge-log.md` 末尾加一节“交叉审查的处理”，每个问题一行：

   ```
   - 审查者 · F编号 · 单元 · 严重度 · 采纳 / 部分采纳 / 不采纳 · 改了什么或为什么不改 · 是否为新的数学修改
   ```

   为处理意见做的修改也算你的修改：属于新的数学修改的，在这一行里注明。
5. 在 `3-combine/` 里运行：
   - `python3 merge_check.py verify --compile`
   - `python3 merge_check.py audit`

   两项都要通过。audit 会核对每个新写、回滚过的单元在日志里都有记录。

## 完成后在聊天里总结

- 每个审查者各多少条问题；采纳、部分采纳、不采纳各多少；
- 逐条列出所有 blocking 问题的处理结果；
- 逐条列出这一轮新做的数学修改（单元和一句话）；
- `verify` 与 `audit` 的结果。

之后由作者重新运行 `python3 run_retention.py`（留存率以修改后的 `final.tex` 为准），再进入第 5 步的统一审查。
