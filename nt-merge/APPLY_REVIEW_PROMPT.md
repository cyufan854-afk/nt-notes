# 处理交叉审查的意见（第 4 步的后半）

把本文件交给第 3 步的**合并模型**（agent 模式，能读写本地文件、能运行命令），它熟悉自己的决定。需要深入判断的问题，它按下文交给**疑难复核模型**（按 `FABLE_PROMPT.md` 工作），与第 3 步的分工相同。

## 材料

都在同一个工作目录里，命令也在这个目录运行。

- `final.tex`：第 3 步的合并结果，就在它上面改。
- `baseline.tex`、`branch1.tex`、`branch2.tex`：只读，用来核对。
- `merge-log.md`、`escalate.md`、`progress.md`：第 3 步的合并说明、疑难清单和复核结论、进度与约定。
- `MERGE_PROMPT.md`：硬约束、疑难单元的标准和各文件的格式。
- `review-<审查者>.md`：审查意见，每个审查模型一个文件，例如 `review-gpt.md`、`review-argon.md`。问题有两种写法：
  - `<<<FINDING Fn>>> … <<<END Fn>>>` 块，含单元、类别、严重度、决定者、final 原文、问题、依据、建议（用 `CROSS_REVIEW_PROMPT.md` 的审查者）；
  - 审查报告里“问题总表”的一行加“每个问题的证据”一节，用表中的 ID 指称（用 `CROSS_REVIEW_AGENT_PROMPT.md` 的审查者）。

## 第一轮：逐条处理

1. 逐条处理每个审查者的每个问题。不同审查者指出同一处时，合并成一条处理。
2. 审查者也可能出错。先回到 baseline、branch1、branch2 核对事实，再决定：
   - **采纳**：修改 `final.tex`。建议的改法不一定最好，你可以按自己的判断改。
   - **部分采纳**：只改其中成立的部分。
   - **不采纳**：写明理由（例如审查者看错了版本、问题在 branch1 里本来就如此且是对的）。
   - **交疑难复核**：符合下面任一情形时，不要自己定：
     - 问题所在的取舍是疑难复核做的（`escalate.md` 里有这个单元，或日志条目末尾有 `· 疑难复核`），而问题涉及取舍或数学内容；
     - 问题涉及数学正确性（blocking，或类别为“新数学修改有误”“其他数学疑点”），而你没有把握，或者你与审查者的判断相反；
     - 不同审查者对同一处的意见互相冲突，且涉及数学内容。

     这时在 `escalate.md` 里新开一节“审查意见”（已有就接着写），每条一行：

     ```
     - [待复核] 单元 thm:4.3.1 · 情形：审查意见（gpt F3；argon F7）· 暂定处理：（你倾向怎么做，final 当前是什么样）· 疑点：（审查者的论点，以及需要判断什么）
     ```

     `final.tex` 先保持原样，或改成你倾向的处理，并在“暂定处理”里写明是哪一种。

   疑难复核做过的单元里，纯粹的引用、LaTeX、日志问题可以直接处理，不必上交。
3. 硬约束与第 3 步相同：
   - `final.tex` 的 label 和 theorem / definition 环境与 branch1 完全相同；
   - 引用按 label 对照改名；
   - 能编译；
   - 不在聊天里输出整份文件。
4. 在 `merge-log.md` 末尾加一节“交叉审查的处理”，每个问题一行：

   ```
   - 审查者 · F编号或 ID · 单元 · 严重度 · 采纳 / 部分采纳 / 不采纳 / 交疑难复核 · 改了什么或为什么不改 · 是否为新的数学修改
   ```

   为处理意见做的修改也算你的修改：属于新的数学修改的，在这一行里注明。
5. 运行 `python3 merge_check.py verify`，必须通过。若工作目录是 git 仓库，提交一次，信息写 `review-comments: apply`。
6. 在聊天里汇报第一轮：每个审查者各多少条问题；采纳、部分采纳、不采纳、交疑难复核各多少；逐条列出所有 blocking 问题的处理结果。

   如果有交疑难复核的条目，到这里停下，等疑难复核完成。没有的话，直接做“收尾”。

## 收尾（疑难复核完成后，或没有需要上交的条目时）

1. 读 `escalate.md`“审查意见”一节的复核结论，把“交叉审查的处理”里对应的行改成最终结果，例如 `交疑难复核 → 改写（见 escalate.md）`。复核结论不要再改；你若认为它有错，写进 `progress.md` 的“未决事项”，留给作者。
2. 运行：
   - `python3 merge_check.py verify --compile`
   - `python3 merge_check.py audit`

   两项都要通过。audit 会核对每个新写、回滚过的单元在日志里都有记录。
3. 在聊天里总结：
   - 每个审查者各多少条问题；采纳、部分采纳、不采纳各多少，交疑难复核的各得到什么结论；
   - 逐条列出所有 blocking 问题的最终处理结果；
   - 逐条列出这一轮新做的数学修改（单元和一句话），注明哪些由疑难复核做出；
   - `verify` 与 `audit` 的结果。

之后由作者重新统计留存率（以修改后的 `final.tex` 为准），再进入第 5 步的统一审查。
