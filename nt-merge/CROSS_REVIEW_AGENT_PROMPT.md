# 讲义分支融合交叉检查提示词

## 使用方法

这是第 4 步的 agent 模式提示词，给能读本地文件、能运行命令的检查模型用（例如 Codex、Antigravity）；只能用网页版粘贴时，改用 `CROSS_REVIEW_PROMPT.md` 和 `make_packet.py`（见 `README_zh.md`）。检查模型选与合并不同家的模型，例如 GPT、Gemini Argon。Opus 和 Fable 分别担任过合并模型和疑难复核模型，不在这一步当检查模型。

第 3 步完成后，把整个工作目录复制一份（或打包成 zip）交给检查模型，不要让它在原目录里工作。目录里应当有 `final.tex`、`merge-log.md`、`escalate.md`、`progress.md`，通常还有 `merge-plan.md`、`merge-audit.md`；有编译日志、git 提交记录或 branch2 的阶段稿，也一并保留。给每个检查模型单独开一个新对话，再复制下方的“提示词正文”。

各模型第一轮使用同一版融合稿，独立检查。先保留各自报告，再交叉复核争议项，避免先看到其他模型的结论而影响判断。检查期间若融合稿发生修改，必须区分版本。

收到报告后，把 `review-report.md` 改名为 `review-<检查者>.md`（例如 `review-gpt.md`），放回工作目录，交给合并模型按 `APPLY_REVIEW_PROMPT.md` 处理。

下面的提示词适用于所有检查模型，无需按模型修改。它对应归档说明中的第 4 步；后续逐个单元的全文数学审查属于第 5 步。

---

## 提示词正文

你负责交叉审查一份英文初等数论讲义的分支融合结果。

共同祖先为 baseline，两个分支为 branch1 和 branch2，待审稿为 final。请对照四份源码，判断融合是否遗漏了有价值的修改、引入错误或造成回退，并核实结构、引用、合并日志和疑难清单。

融合由两个角色完成：合并模型处理全部单元，并把需要深入判断的疑难单元做暂定处理后列入 `escalate.md`；疑难复核模型逐条裁决这些单元，它的结论就是最终决定。两者的说明分别是 `MERGE_PROMPT.md` 和 `FABLE_PROMPT.md`。

请直接检查，交付可供融合模型逐条处理的审查报告。保留四份输入稿不变；本轮只提出修补建议。允许编写只读分析脚本、运行检查和编译，也可以在隔离的临时副本中验证候选补丁。

### 一、审查原则与范围

1. 独立判断每个实质改动。作者身份、模型名称、此前审查次数、合并日志中的解释，都不能代替内容证据。即使你曾参与融合，也从四份文件重新核查。
2. 按数学正确性、证明完整性和表述准确性判断取舍。某处分支修改未保留，可能是合理回滚；需要指出它具体改善了什么，以及最终稿为何失去了该改善，才能判定为回退。
3. 不以保留率作为质量标准。语义等价的改写、合理的错误修复、为遵守编号约束而调整写法，都可能是正确融合。
4. 检查所有差异及其依赖。对数学变化，必须读完整陈述和证明，并追踪受影响的定义、所用结果和下游用途。未变区域只要与改动相关，也须核查。
5. 本轮重点是融合正确性。顺带发现的历史遗留数学问题单列，并说明它在 baseline、branch1、branch2 中的存在情况。不要因此跳过差异检查，也不要声称完成了全文所有定理的独立验证。
6. 结论必须有证据。区分“已确认错误”“待核实疑点”和“可选建议”。不设发现数量上限，也不为凑数提出修改。主报告以正确性、信息损失和实质可读性问题为主，纯风格偏好单列。
7. 如果工具、附件或上下文容量限制了检查，明确记录已检查范围和未完成部分。抽样检查不能表述为全面通过。

### 二、识别材料并建立可追溯的输入

先列出实际收到的文件及其用途。能运行命令时，记录四份源码的文件名和 SHA-256，保证报告对应明确版本。

所有材料都在同一个目录里：

| 文件 | 用途 |
|---|---|
| `baseline.tex` | 两分支的共同祖先 |
| `branch1.tex` | 最终编号结构的依据，也是一个内容候选来源 |
| `branch2.tex` | 另一个内容候选来源 |
| `final.tex` | 本轮待审融合稿 |
| `merge-log.md` | 取舍说明；疑难复核的结论以条目末尾的 `· 疑难复核：…` 标出 |
| `escalate.md` | 疑难单元清单：合并模型的暂定处理和疑点，以及每条的复核结论 |
| `progress.md` | 合并进度、后续章节须遵守的约定、未决事项 |
| `MERGE_PROMPT.md` | 本次融合的要求和硬约束，以及疑难单元的标准（A–D） |
| `FABLE_PROMPT.md` | 疑难复核模型的工作说明 |
| `merge_check.py` | 合并计划、结构检查和日志覆盖辅助工具 |
| `retention.py` | 上一脚本的依赖，也提供文本改动留存统计 |

目录里其他步骤的文件（`CROSS_REVIEW_PROMPT.md`、`APPLY_REVIEW_PROMPT.md`、`make_packet.py`、`cross-review-*.md` 等）与本轮无关。忽略 `__MACOSX/` 下的元数据。若存在多个 final，先确认待审版本，不要混用。

读完 `MERGE_PROMPT.md` 后，先独立建立差异清单、判断正文，再对照合并日志和疑难清单。日志和清单用于核对决定，不能决定你检查哪些地方。缺少日志时继续审查正文，并把日志核对列为未完成。若缺少 final，则先完成参考材料分析，明确还不能判断融合结果。

### 三、建立四方对照和完整改动清单

#### 1. 先按内容确认单元对应关系

定理或定义连同证明、替代证明、附注、例子和承接文字，构成需要一起判断的内容。还要覆盖导言区、全局约定、标题下说明、引言、表格、图、索引和文末材料。

用章节位置、标题、陈述和证明识别同一单元。branch1 新增过带编号环境，旧 label 可能仍存在，却已经属于另一个内容。请人工核查自动配对，并允许一个旧单元在新版中拆成多个内容部分。

以四份文件中内容的并集建立清单。明确处理新增、删除、迁移和拆分的文字，防止只遍历 branch1 或 final 中仍存在的单元，漏掉已经消失的内容。

#### 2. 建立四个方向的差异

- baseline → branch1：branch1 做过哪些改动。
- baseline → branch2：branch2 做过哪些改动。
- branch1 → final：融合稿撤回、改写或加入了什么。
- branch2 → final：branch2 中哪些内容未被采用，以及如何处理。

对照时区分排版变化、引用迁移和实质改动。忽略普通换行、缩进可以帮助阅读，但保留原始差异以核查 TeX 语义。不要把空行、`%` 注释边界、宏参数中的空格或数学符号变化一概视为无意义。

#### 3. 逐项确认改动的最终去向

按实质改动记录以下信息。一个单元可能包含多个互相独立的改动，不能只给整个单元一个“已保留”标签。

| 字段 | 要记录的内容 |
|---|---|
| 定位 | final 的 label 或章节、四稿对应位置、必要的短引文 |
| 来源变化 | 相对 baseline，哪一边改了什么 |
| final 的处理 | 原样保留、语义等价保留、合理回滚、部分保留、融合改写、遗漏或未判定 |
| 判断依据 | 为什么这种处理正确、有问题或尚无法判断 |
| 关联位置 | 受影响的定义、证明、引用或后文用途 |

若改进迁移到了别处，指出实际位置。若两份文字意义相同，说明关键等价关系。逐项追踪有效修补的去向，尤其留意同一单元内部“保留了润色，却丢了条件或证明步骤”的情况。

### 四、检查编号结构与 LaTeX 完整性

按 `MERGE_PROMPT.md` 的硬约束核查 final。

1. theorem / definition 环境及其 label 的个数、顺序、名称与 branch1 一致。检查有没有新增、删除、拆分、合并或调换带编号环境，也检查其他环境、计数器命令和编号定义是否造成绕过约束的变化。
2. 全部 `\label{…}` 的序列与 branch1 比较。归档脚本实际比较的是全部 label，不能只比较 theorem / definition 的编号 label。branch2 的额外别名 label 也需要处理。
3. 核对实际编译编号与 label 名称，分别检查定理、定义计数器及小节顺序。label 列表相同仍不能证明内容位置和引用意义正确。
4. 检查环境的嵌套顺序、花括号、数学模式、枚举及证明边界。只比较 `\begin` 与 `\end` 的数量不足以验证嵌套。
5. 核查导言区与 branch1 的差异。检查 branch2 搬入的宏、环境、图表、索引及链接是否还有完整依赖。归档脚本会把导言区不同列为检查失败；日志有解释也不会自动消除该失败。
6. 搜索冲突标记、占位符、截断句、重复段落、重复证明和意外删除。检查搬运后的段落、图表或证明是否仍属于正确的单元。
7. 能编译时，在隔离目录运行完整编译，保留退出码和关键日志。检查未定义命令、引用、重复 label 和编号不符。区分编译错误、实质排版问题与普通排版警告。

编译成功只说明通过了相应技术检查。数学结论和引用目标的语义仍需继续核查。

### 五、逐项检查内容取舍和数学影响

#### A. 只有一边改动的内容

核对该边每个有效改进是否保留。未保留时，先判断原改动是否有错、是否已由另一种写法实现，再判断是否构成遗漏或回退。对新增条件、边界情形、量词、定义澄清、证明步骤和引用纠错，逐项说明去向。

#### B. 两边都改动的内容

分别读懂 baseline、branch1、branch2，再评价 final 的处理。把一个单元中的独立修补分开核对，防止整块选边时丢失另一边修好的问题。

重点检查以下组合错误。

- 采用一边的陈述，却配上只适用于另一边条件的证明。
- 采用一边的定义，却保留另一边对术语、记号或适用范围的理解。
- 两边各自合理的局部修改，组合后出现遗漏、矛盾或重复。
- 定理分项、变量名、模数、索引或例外情形改了，后续文字仍沿用旧版。
- 把另一边补上的关键步骤删成“显然”，使证明再次出现缺口。
- 引用文字已改，目标或调用条件仍属于旧版。

#### C. final 自行新增或改写的内容

从正文差异识别全部新增数学变化，不限于日志承认的条目。审查新的条件、公式、量词、结论及推理步骤，包括藏在英文润色中的数学变化。

检查每一步是否由当时可用的前提推出，以及证明是否落实陈述的每一个分项。按相关内容检查零、负数、单位、常数或零多项式、最小参数、小素数、空和空积、分母非零、互素性、整除与可逆性、等号及端点情形。边界检查应由实际定义和改动触发，不要机械套用。

怀疑结论有误时，尽量给出满足前提的明确反例。怀疑证明有缺口时，定位到具体推理，并检查全文约定或既有结果能否补足。小规模计算可以检验例子或反驳命题，不能代替一般证明。

#### D. 定义变化和跨单元影响

比较全局约定、定义、定理陈述、证明和下游使用。检查局部修复是否让其他位置失效，或让引言、表格、示例与正文不一致。

需要引用后文时，核查其证明是否反过来依赖当前结果，或依赖一条路径最终回到当前结果。单纯的前向引用不自动构成错误；请给出实际的循环依赖路径，或指出尚未验证的依赖。

### 六、单独检查引用的语义

引用必须同时满足三个条件：目标存在、目标身份正确、目标内容足以支持当前用法。

1. 核查所有受编号变化、内容迁移或分项调整影响的引用，以及 final 中新增、改写的引用。对未改文本中受影响的引用也要检查。
2. 覆盖 `\ref`、`\eqref`、`\cref`、`\Cref`、`\autoref`、`\pageref`，也覆盖 `\hyperref[…]`、超链接锚点及正文手写编号。检查 “Definition / Theorem / Lemma” 等称谓是否与实际目标一致。
3. 检查指向分项的 `(a)`、`(b)` 和 “the preceding result”“the second proof” 等相对指代。目标编号正确时，分项和相对位置仍可能错误。
4. 旧单元被拆分时，按该处真正调用的内容选择目标。禁止只凭旧 label 做全文机械替换。
5. branch2 的描述性别名 label、标题锚点或额外环境未进入 final 时，查找全部相关链接与文字说明，确认它们已改为有效目标。

本归档有以下检查线索。不能据此预判尚未提交的 final 有错。

- baseline 的 `def:5.7.1` 包含 average order 和渐近记号。branch1 将两者分开，`def:5.7.1` 是 asymptotic notation，average order 位于 `def:5.7.2`；branch2 则将渐近记号移至文首的 `sec:asymptotic-notation`。调用 average order 与调用渐近记号的文字，可能需要不同目标。
- branch2 含额外别名 label、`\hyperref`、索引及专用宏，例如 `\statementlist`；branch1 使用 `\statementitems`。搬入内容时要核查链接及宏环境的完整性。其新增内容应分别按价值、依赖和结构约束判断。
- 自动配对已有一个误报实例。baseline 和 branch1 都有 `def:9.4.1`，定义主体一致，标题从 strong probable prime 改为 the strong test；当前辅助计划却将其列为找不到对应环境。应按实际内容确认对应关系，不能据此认定定义丢失。

### 七、核查合并日志和辅助工具结果

完成独立正文判断后，再将差异清单与 `merge-log.md` 逐条核对。

- 单边改动的全部或部分回滚，是否记录准确。
- 两边都改动的冲突处理，是否记录所作取舍及理由，包括直接选择某一边的情形。
- 两边都没有的数学修改和非数学优化，是否全部记录。
- 日志中的说明是否与实际源码一致，有无“声称已保留，实际已丢失”的情况。
- 未动手的大问题，以及 branch2 的 label、编号环境、导言区变化，是否交代处理方式。
- 条目定位是否正确，理由是否解释了实质决定。一个单元只有一次提名，不能证明其内部多个决定都已说明。

然后核对 `escalate.md` 和 `progress.md`：

- 符合 `MERGE_PROMPT.md` 中疑难单元标准（A–D）、却没有列入 `escalate.md` 的单元。这类单元只经过合并模型一方判断，要重点检查。
- 每条复核结论（维持、改写、交作者）是否与 final 和 `merge-log.md` 中的 `· 疑难复核` 记录一致；改写是否仍在硬约束和“小幅”修正的界限之内。
- 标为“交作者”的条目，final 当前处于什么状态，是否会误导读者。
- `progress.md` 的“约定”在后续章节是否得到遵守；“未决事项”有没有遗留未处理、也没有交代去向的。
- 复核结论同样按内容判断，不能因为出自疑难复核就视为正确。

辅助脚本只能提供部分证据。使用前读源码，至少注意以下限制。

1. `plan` 的配对依赖标题、正文相似度、局部分组和顺序假设。人工核实新增、拆分、迁移及配对失败的单元，避免错误映射掩盖差异。
2. `audit` 主要比较规范化后的单元文字，并通过日志是否含有单元 ID（按完整 ID 匹配）判断部分覆盖。它不理解理由是否成立，也不能证明每次冲突处理都已有实质说明。它也不读取 `escalate.md`。
3. `verify` 不能验证数学，也不能验证引用的实际含义。它的引用正则未覆盖全部链接写法，环境数量检查也不能验证完整嵌套。
4. `retention.py` 的“保留 / 撤回 / 改写”是文本统计。等价改写可能记作改写，原样保留的文本也可能已与新上下文冲突。不要把统计状态直接转成质量结论。
5. 自动单元切分和只遍历仍存在单元的报告，可能遗漏无编号内容、跨单元变化或已消失文字。用原始差异和四稿内容清单补查。

#### 能运行工具时

把收到的目录整份复制到一个隔离的临时目录，在副本里运行；收到的原目录保持不变。`audit` 从脚本所在目录读取 `merge-log.md`，所以脚本、稿子和日志要留在同一个目录。在副本目录里运行：

```bash
python3 merge_check.py plan --root . --out merge-plan-review.md
python3 merge_check.py verify --root .
python3 merge_check.py verify --root . --compile
python3 merge_check.py audit --root . --out merge-audit-review.md
```

缺少日志时，跳过日志 audit 或如实记录失败原因，继续其他检查。若 Python、依赖或 TeX 工具不可用，记录实际原因，并完成可行的静态和内容检查。没有运行的命令必须标为未运行。

留存统计可作为额外定位工具，使用中性来源名称：

```bash
python3 retention.py --final final.tex \
  --source branch1 baseline.tex branch1.tex \
  --source branch2 baseline.tex branch2.tex \
  --out branch-retention-review
```

这只能统计“各分支相对 baseline”的变化。缺少某个模型修改前后的独立快照时，不能把 branch1 或 branch2 的整体统计冒充该模型个人贡献的保留率。

### 八、输出可逐条处理的审查报告

中文解释，英文原文和 LaTeX 片段保留原样。正文使用 Markdown，候选补丁使用代码块。不要把含 LaTeX 的正文放进 JSON 字符串，也不要输出整份融合稿。

#### 1. 审查结论与范围

选择以下状态之一，并给出依据。

- `发现需修正的问题`：已确认存在数学、融合、结构或引用错误。
- `正文暂未发现错误，但日志或检查尚不完整`：正文未确认出错，但仍有日志缺口、未核实疑点、未完成覆盖或必要技术检查未执行。
- `在已声明的完整融合检查范围内未发现问题`：完成了本提示词要求的差异及依赖检查，并清楚列出技术验证结果。仍不得扩大为“全文所有数学内容绝对无误”。

列明四稿版本、实际检查范围、未完成部分及工具结果。“未运行”“失败”“通过”分别记录，不把它们合并成“基本通过”。

#### 3. 每个问题的证据

每条报告包含：

- final 的 label、相关分项、文件行号或可唯一定位的短引文。
- baseline、branch1、branch2、final 的关键差异。只引用证明判断所需的片段；某稿无此内容时明确写明。
- 具体错误、信息损失或证明缺口。给出反例、失败推理、引用目标内容或其他可核查依据。
- 对本处和下游的影响，以及它为何属于上述来源类别。
- 满足现有编号约束的最小修补建议。必要时附局部 LaTeX 替换片段或 unified diff，并说明验证情况。

确认错误必须有足够证据。证据不足的项目列为疑点，并写出要验证什么。若所需修复超出原合并允许的局部修改范围，或必须改变编号结构，单独标记交作者决定。

#### 4. 覆盖记录

能写文件时，交付 `review-report.md` 和 `review-coverage.md`。后者按章节、单元和实质改动记录核查状态；问题总表中的 ID 应能对应到覆盖记录。无需在聊天中粘贴全部已通过条目。

至少分别交代这些类别的覆盖：单边变化、双方变化、branch1 新增内容、branch2 新增或迁移内容、final 自行改写、编号与引用、导言区与无编号材料、日志核对、疑难清单与复核结论。

不能写文件时，在回复中提供报告和覆盖清单。若本轮无法完成，保留已确认发现，并给出已审单元、待审清单和下一起点。不要用“其余应无问题”代替尚未完成的检查。

请从文件清单和独立差异分析开始，持续完成可做的检查，最后提交上述报告。
