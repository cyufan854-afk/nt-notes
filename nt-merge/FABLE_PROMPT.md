# 给疑难复核模型的操作说明（第 3 步：疑难单元）

你在一个新对话里工作，负责复核一次三方合并中的疑难单元。你需要 agent 模式：能读写本地文件、能运行命令。

## 背景

这是一份英文 LaTeX 初等数论讲义（约 13,500 行、三百多个定理、一百多个定义）。`baseline.tex` 是共同祖先，`branch1.tex` 和 `branch2.tex` 是从它分出的两个分支。合并模型以 branch1 为底稿，逐个单元合并出 `final.tex`，每个单元都已经做出了处理。其中需要深入判断的单元，合并模型列在 `escalate.md`，并写了暂定处理和疑点。所有文件都在同一个工作目录里，命令也在这个目录运行。

**你的结论就是这些单元的最终决定。** 合并模型在后续章节会以你的处理为准，并遵守你写下的约定。

开始前先读 `MERGE_PROMPT.md` 全文，了解两个分支的来历、硬约束、“可以自己决定的”范围和日志格式。那份说明里的硬约束、“小幅”数学修正的界限和日志格式对你同样适用；其中“分批”和“工作方式”是写给合并模型的，你按本文件工作。

## 范围

只处理用户指定的那一节（例如“第 2 批”，或者第 4 步之后的“审查意见”）中标为 `[待复核]` 的条目。

## 逐条怎么做

1. **定位**：在 `final.tex` 里找到该单元。baseline 中的对应 label 见 `merge-plan.md` 的对照；branch2 的 label 与 baseline 相同。
2. **先独立判断**：先读 baseline、branch1、branch2 中该单元的全文，以及判断所需的上下游（它用到的定义和结果、引用它的地方），自己形成判断。然后再读 `final.tex` 的当前文字，以及条目里的暂定处理和疑点。暂定处理只是起点：不要默认维持它，也不要为了显得独立而改它。
3. **决定**，三选一：
   - **维持**：`final.tex` 不动。
   - **改写**：直接在 `final.tex` 上改这个单元。硬约束全部适用；数学修正限于“小幅”（局部的修正，不改变定理的含义和证明的整体结构）。
   - **交作者**：问题超出小幅修正的范围，或者需要增删带编号的环境、改 label、改导言区。`final.tex` 保持暂定处理，或者改回你认为更稳妥的一边，并写明。
4. **下游**：改写若影响别处（记号、定义、条件、分项编号），只做保持引用正确所必需的改动；其他需要跟着改的地方不要动，写进该条结论的“影响”。若影响到尚未合并的后续章节，在 `progress.md` 的“约定”里加一条，注明来源为“疑难复核”。
5. **不限于条目写到的疑点**：你在该单元里发现的其他问题，一并处理或记下。清单以外的单元若有问题，不要改，记在本节末尾的“复核者另见”下面。

## 记录

**escalate.md**：把 `[待复核]` 改成 `[维持]`、`[改写]` 或 `[交作者]`，并在条目下加一行：

```
  - 复核：（一两句理由；改写时写改了什么，必要时附改前改后的关键片段）· 影响：（无 / 涉及哪些单元）
```

**merge-log.md**：在该单元的条目末尾追加 `· 疑难复核：维持 / 改写 / 交作者 —（一句话，改写时写清改后的样子）`。不要删改合并模型原来写的部分。若该单元还没有条目，而你的处理使它需要一条（见 MERGE_PROMPT.md 的“必须说明的”），按同样格式新加一条，并在末尾标上 `· 疑难复核`。

## 完成

1. 运行 `python3 merge_check.py verify`，必须全部通过。
2. 若工作目录是 git 仓库，提交一次，信息写 `batch K: review`（处理审查意见时写 `review-comments: review`）。
3. 在聊天里汇报：
   - 本节复核了多少条，维持、改写、交作者各多少；
   - 逐条列出“改写”和“交作者”（单元 id 和一句话）；
   - 新写进 progress.md 的约定；
   - “复核者另见”的条数；
   - `verify` 的结果。

## 不要做的

- 不要处理范围以外的条目，不要改清单以外的单元（保持引用正确所必需的除外）。
- 不要改 label、带编号的环境和导言区。
- 不要为了让任何一方的“保留率”更高或更低而做决定。
- 不要在聊天里贴整份文件或大段单元全文。
