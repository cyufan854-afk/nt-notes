# 给合并模型的操作说明（第 3 步：branch1 + branch2 → final.tex）

把本文件整份交给负责合并的模型（agent 模式，能读写本地文件、能运行命令）。你的目标是做出**最好的最终稿**：取舍、融合、回滚、在冲突处重写，以及小幅的数学修正和自行优化，都由你按内容判断。只有下面几条硬约束不能违反，你做的每个实质决定都要说明。

本步骤由两个模型分工完成。你处理**全部**单元；其中需要深入判断的**疑难单元**，你照常做出暂定处理，同时列入清单，由另一个模型（下称“疑难复核模型”，在新对话中按 `FABLE_PROMPT.md` 工作）分批复核。疑难复核的结论就是这些单元的最终决定，你在后续章节要遵守它记下的约定。

不要写自动合并脚本，也不要用 `git merge-file` 之类的工具直接产出结果。你要逐个单元看过、在文件上动手。`merge_check.py` 是给你的辅助工具，只列信息、做检查，不改文件。

## 文件

所有文件都在同一个工作目录里（下称“本目录”），命令也都在本目录运行：

| 文件 | 是什么 |
|---|---|
| `baseline.tex` | 共同祖先。branch1 和 branch2 都从它分出来（不要改） |
| `branch1.tex` | 作者一侧的最新版：多轮前沿模型数学审查、Muse Wonder 一轮、作者的手工修改（不要改） |
| `branch2.tex` | 27B 模型一侧：全文英文润色，以及经复核后采用的 DeepSeek 审计表 LOW 条目修补和引用核查修补（不要改） |
| `1-polish.tex`、`2-triage.tex`、`3-refs.tex` | （有的话）branch2 的阶段稿，按这个顺序，可以看出 branch2 的每处修改出自哪一步 |
| `final.tex` | 你的产物（由你创建；疑难复核模型会改动其中的疑难单元） |
| `merge-log.md` | 你的说明（由你创建；疑难复核模型会在疑难单元的条目末尾追加结论） |
| `escalate.md` | 疑难单元清单（由你创建；疑难复核模型在每条下写结论） |
| `progress.md` | 进度、约定和未决事项（由你创建并随时更新，用于中断后或换会话后继续） |

本目录里还有其他步骤的提示词和脚本（`CROSS_REVIEW_*`、`APPLY_REVIEW_PROMPT.md`、`make_packet.py` 等），与你这一步无关，不要改。

这是一份英文 LaTeX 初等数论讲义（约 13,500 行、约 200 页、三百多个定理、一百多个定义）。判断一处改动是谁做的、改了什么，永远以 baseline 为参照，三份一起看。

## 开始之前

**如果 `progress.md` 已经存在**，说明合并正在进行：先读它，再读 `escalate.md` 里已复核条目的结论（尤其是上一批）和 progress.md 里的“约定”，然后从记录的位置继续。不要重做已完成的批次。

**如果是第一次开始**：

1. 运行 `python3 merge_check.py plan`，读生成的 `merge-plan.md`：
   - 每个单元（一个定理或定义连同其后的证明，或标题下的一段说明文字）被哪一边改过；
   - baseline → branch1 的 label 对照。branch1 新增过带编号的环境，后面的 label 顺延；对照是按标题和正文自动配对的，请逐条核对。已知一处误报：`def:9.4.1` 在 baseline 和 branch1 中主体相同、只改了标题，plan 却列为“找不到对应环境”。
2. 以 `branch1.tex` 为底稿复制出 `final.tex`。
3. 按下文格式建立 `escalate.md` 和 `progress.md`，然后从第 1 批开始逐个单元处理。

## 硬约束（不能违反）

1. **label 与带编号的环境**：`final.tex` 里的 theorem / definition 环境及其 `\label` 必须与 `branch1.tex` 完全相同，个数、顺序、名字都一样。label 按编号命名，与实际编号一致；不能新增、删除、拆分、合并或调换带编号的环境，也不能改 `\label{…}`。若你认为某处确实需要增删环境，写进日志留给作者。
2. **引用按对照改写**：从 branch2（或 baseline）搬来的文字里，凡是 `\ref{…}`、`\eqref{…}` 指向在 branch1 里改了名的 label，都改成 branch1 的名字。例如截至写这份说明时，baseline 的 `def:5.7.1`（average order）在 branch1 里是 `def:5.7.2`；以你运行 `plan` 时看到的对照为准。
3. **能编译、引用都能解析**：`python3 merge_check.py verify --compile` 全部通过。
4. **不在聊天里输出整份文件**，也不贴大段单元全文；直接在文件上改，聊天里只报进度。

## 你可以自己决定的

- **只有一边改过的单元**：通常采用改过的那一边。但如果你判断那处改动是错的、改坏了、或不如原文，可以回滚，也可以在它的基础上再改。
- **两边都改过的单元**：选一边、把两边融合，或者重写，按你认为最好的来。branch1 的数学修改经过多轮审查，分量较重；branch2 的润色和修补也可能修到了 branch1 没注意的地方。不必默认偏向任何一边。
- **小幅的数学修正**：发现错误、遗漏的条件或步骤、公式笔误时，可以直接改。“小幅”指局部的修正，不改变定理的含义和证明的整体结构。更大的问题写进日志，交给第 5 步。
- **自行优化**：表述、衔接、前后一致性（记号、术语、写法）上的改进可以做，但不要为改而改。

不要为了让任何一方的“保留率”更高或更低而做决定：合并之后会统计 27B 和 Muse Wonder 两组改动在最终稿里保留、撤回、改写的比例，这个统计只有在你按内容决定时才有意义。

## 必须说明的（输出时要说明）

下面这些情形，每一处都在 `merge-log.md` 里写一条。格式固定，便于作者和工具核对：

```
- 单元 thm:4.3.1 · 类型：回滚 / 冲突处理 / 新的数学修改 / 自行优化 · 改了什么：（一两句，必要时附改前改后的关键片段）· 理由：（一两句）
```

- **回滚**：只有一边改过、你没有采用（或部分没有采用）那一边的修改。
- **冲突处理**：两边都改过，你选了一边、融合，或者重写。
- **新的数学修改**：两边都没有、由你新做的数学修正（条件、步骤、公式、结论），无论多小。
- **自行优化**：两边都没有、由你新做的非数学修改。
- 另外列出：你注意到、但按“小幅”的界限没有动手的数学疑点；branch2 若改动了 label、编号环境或导言区，你怎么处理的。

单元 id 写最终稿里的 label（说明文字单元用 `merge-plan.md` 里的 id）。`merge_check.py audit` 会逐单元判断最终稿取自 branch1、branch2、baseline，还是新写的文字；凡是“新写”或“回滚了只有一边做过的修改”的单元，日志里都必须提到它的 id，否则 audit 不通过。

疑难复核模型会在它复核过的单元条目末尾追加 `· 疑难复核：…`。不要删改这部分。

## 分批与疑难单元

### 批次

按 `\section` 分六批（节号即 label 的首位数字）。单元数是本包 branch1 中至少一边改过的单元，仅供参考。

| 批 | 范围 | 约需处理单元 |
|---|---|---|
| 1 | 导言区、Notation and Conventions、§1–§3 | 83 |
| 2 | §4–§5 | 78 |
| 3 | §6 | 63 |
| 4 | §7 | 66 |
| 5 | §8–§9 | 86 |
| 6 | §10–§12 | 63 |

只做当前批次范围内的单元。处理本批时若发现前面批次的内容需要改，不要回头改，记进 progress.md 的“未决事项”，全部批次完成后统一处理。

### 什么是疑难单元

符合下列任一情形的单元：

- **A**：两边都改动了数学内容（陈述、条件、量词、公式、证明步骤），而不只是措辞；
- **B**：你无法确定某一边的改写（尤其是 branch2 的润色）有没有改变数学含义；
- **C**：你打算做“新的数学修改”；
- **D**：引用目标因单元拆分或改名需要按语义判断（例如 baseline 的 `def:5.7.1` 在 branch1 里拆成了 `def:5.7.1` 渐近记号和 `def:5.7.2` average order），或者需要从 branch2 搬入宏、锚点、额外 label（例如 `\statementlist`、`sec:asymptotic-notation`）。

只列真正需要判断的单元。不要因为单元长、改动多，或者只是措辞上难以取舍，就列入清单。

对疑难单元，你仍然要：

1. 做出暂定处理，保证 `final.tex` 始终完整、`verify` 能通过；
2. 按“必须说明的”在 merge-log.md 写条目；
3. 另外在 escalate.md 写一条。

### escalate.md 的格式

```
## 第 1 批（导言区、Notation and Conventions、§1–§3）

- [待复核] 单元 thm:2.2.4 · 情形：A · 暂定处理：（一句）· 疑点：（需要复核者判断什么）
```

一个单元一条；同一单元有几个独立疑点，在“疑点”里分条写。疑难复核模型会把 `[待复核]` 改成 `[维持]`、`[改写]` 或 `[交作者]`，并在条目下加一行结论。

### 复核之后

开始下一批之前，读上一批每条的结论：

- 已复核的单元以疑难复核的处理为准，不要再改。你若认为它有错，记进 progress.md 的“未决事项”，留给第 4 步。
- 疑难复核模型写进 progress.md “约定”的记号、术语、定义上的决定，后续章节要遵守。
- 若用户让你在上一批复核完成之前就开始下一批，照做。等那一批的结论出来，下次开始前补读一遍，并检查已经做完的单元是否要按新约定调整；需要调整的直接改，照常记日志。

### progress.md 的格式

```
# 合并进度

- 已完成批次：1、2
- 当前批次：3（§6），已处理到：thm:6.2.4
- 本批计数：处理 N 个单元（两边都改过 M 个）；回滚 a、冲突处理 b、新的数学修改 c、自行优化 d；列入疑难 e 条

## 约定（后续章节须遵守）

- （记号、术语、定义取舍上的决定；注明来源：合并 / 疑难复核）

## 未决事项

- （需要回头处理或留给第 4 步的事）
```

每处理完一节，或者在任何可能中断的时候，更新一次 progress.md，保证换一个会话也能从记录的位置继续。

## 工作方式

- 按单元顺序推进；每完成一节，运行一次 `python3 merge_check.py verify`，并更新 progress.md。
- 聊天里只报进度，例如“§4 完成：两边都改过的 12 个单元已处理，新的数学修改 2 处，列入疑难 3 条”。
- **每批结束时停下**：
  1. 运行 `verify`；
  2. 若本目录是 git 仓库，提交一次，信息写 `batch K: merge`；
  3. 在聊天里汇报：本批处理了多少单元（两边都改过的多少）；回滚、冲突处理、新的数学修改、自行优化各多少处；列入疑难多少条、占本批单元的比例；`verify` 的结果。

  然后等待。不要自行开始下一批。

## 完成标准

六批及各批的疑难复核全部完成后：

1. 处理 progress.md 里的“未决事项”中不涉及已复核单元的部分，照常记日志；涉及已复核单元的，留给第 4 步。
2. `python3 merge_check.py verify --compile` 全部通过。
3. `python3 merge_check.py audit` 通过：每个需要说明的单元都在 `merge-log.md` 里。`merge-audit.md` 留着给作者看。
4. `escalate.md` 里没有 `[待复核]` 的条目。
5. 在聊天里给一段总结：
   - 处理了多少单元，两边都改过的有多少；
   - 回滚、冲突处理、新的数学修改、自行优化各多少处；
   - 疑难单元共多少条，复核结果维持、改写、交作者各多少；**逐条列出“交作者”的条目**；
   - **逐条列出所有“新的数学修改”**（单元 id 和一句话），注明哪些经过疑难复核改写；
   - `verify` 与 `audit` 的结果。

之后是第 4 步：其他模型会对照这四份稿子交叉审查合并结果（丢失的修改、冲突处理、回归、引用改名、新写的数学修改、日志和疑难清单有没有漏记），审查意见会交回来请你逐条处理（说明见 `APPLY_REVIEW_PROMPT.md`）。其中需要深入判断的，同样列进 escalate.md（新开一节“审查意见”），交疑难复核模型。再之后是第 5 步，对每个单元做一次多模型数学审查。
